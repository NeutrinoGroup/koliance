## 1. 术语表（先读，本仓有同形异义词）

| 词 | 本 ADR 中的含义 | 本仓的其它含义（**勿混**） |
| --- | --- | --- |
| **上游 / 调用方** | **发起 HTTP 请求的客户端**：浏览器页面、前端 BFF（`src/app/api/*` 的 route handler）、第三方 Agent | `` `upstream/main` ``（git remote）· **上游数据源**（Alpaca / Pyth / Steam / GitHub / Stripe） |
| **原始报错**（raw error） | 程序内部的技术细节：error 链的 `Error()` 文本、栈、SQL 与约束名、DSN、**环境变量名与其值**、第三方响应原文、文件路径 | — |

## 2. 背景：为什么必须有一个统一体系，而不是逐个 handler 改文案

**现状不是"没有报错"，而是"报错的形态由每个 handler 各自决定"**（实测）：

| 事实 | 证据 |
| --- | --- |
| 响应体的 `error` 字段**就是 `err.Error()`** | `router.go` 与 `middleware.go` 共存在 **4 类错误出口**：① 51 处 `jsonError`（`router.go` 47 处 + `middleware.go` 4 处）；② `router.go:670-675` 1 处手写 map（`verifier/verify`）；③ `router.go:703-810` 12 处 `jsonEnvelope`（其中 `:721,751,780,810` 4 处拼接了 `err.Error()`）；④ `router.go:519` 隐蔽 200 OK 伪成功夹带 `err.Error()` |
| 内部技术细节**已经在流向浏览器与诊断面** | 安全审计在 01 环新发现 **3 个 P0 泄漏点**：<br>1. `SEC-P0-1`（`health.go:311-315` & `:91,102`）：探针 `probeSteam` 网络错误时 `*url.Error` 会将含 `?key=<STEAM_API_KEY>` 的完整 URL 写进 `/healthz` 的 `probes.steam.error`；<br>2. `SEC-P0-2`（`router.go:519` & `:418`）：`ExecuteTrade` 在 200 OK 分支将含 Alpaca 256B 响应原文的 `err.Error()` 赋给 `res.Message`；<br>3. `SEC-P0-3`（`reqlog.go`）：截断上游响应体前缀与反引号/引号 DSN 可能绕过脱敏 |
| 前端有三个互不相干的错误通道 | `src/lib/api.ts` 读 `body.error`（`errorDetail():302`）· `src/app/api/market/route.ts:51` 的 `refuse()` 自造 `{error, reason}` · 各组件 `setError(err?.message)` 各自兜底（`PositionPanel.tsx:292,323`、`DemoControlPanel.tsx:211,256`） |
| 于是**同一件事有两种成熟度的说法** | 后端说 `"market data unavailable: ALPACA_API_KEY/ALPACA_API_SECRET are not configured"`（503），前端词表 `marketFeed.ts:256` 说 `"行情数据源未配置"` + 一句行动建议。D4 的红线就在这里：**后端与前端各自维护业务语言，改一处不改另一处，没有任何判据会发现** |
| 用户看到的仍是笼统文案 | issue #33 原文：PositionPanel / DemoControlPanel 只显示"未配置"，**看不出下一步该做什么** |

**issue #33 的建议是"把后端的缺项透传到 UI"——即"让后端多说"**。
**用户裁定与它方向一致但边界更硬**：后端的详细原因**只落日志**，**不许**进响应体；
响应体里给的是**为该受众写好的业务语言**。二者不冲突，但**必须同时读**，
否则会把"透传"实现成"继续泄漏"。

> **本仓已有的教训，与本决策同族**：`docs/changes/032` 记载过一次判据修正——
> 把**禁词表**改成**性质断言**。本 ADR 的验收判据（§4.2）因此不取"禁止出现某串"，
> 而取**闭集**：响应体里的文案必须能在词表里查到。

## 3. 决策

**总纲：后端是报错体系的唯一设计者与处理者；前端只负责呈现与本地化。**
四条为用户裁定，逐条给"可执行落点"；第 5、6 条为使这四条**可判**而必需的派生决定（已标注）。

### 3.1 【裁定 1】报错处理体系迁移到后端

- **后端**拥有：错误**分类**、**词表**、**响应体形状**、**日志留痕**。
- **前端**只做三件事：按 `code` 查表渲染、本地化、把可操作信息放进取景框。
- **落点**：`FAILURE_COPY`（`marketFeed.ts:255-272`）**收缩**为"词表 → 展示"的映射层，
  不再自行判断"这是 not-configured 还是 unreachable"。分类信息由后端随响应给出。
- **不迁移的部分**（划界，避免矫枉过正）：
  - **纯前端错误**（组件内异常、`fetch` 不发包的 DNS/连接失败）仍由前端处理——
    后端**不可能**描述一个从未到达它的请求。`classifyStatus()` 的 `unreachable` 分支（`api.ts:330,346`）保留。
  - **事实说明型文案**（不是错误）：`marketFeed.ts:107` 的 `NO_SERIES_NOTE` 说的是
    "上游只发布两个观测值，故不画曲线"，**不是失败**。留在前端。

### 3.2 【裁定 2】原始报错由「中间件」做日志记录 —— 且**不改响应体**

这是本次最容易被实现偏的一条，故把职责边界与架构机制写死：

**架构机制（`*errSlot` 堆指针槽位）**：
- 在 `loggingMiddleware`（`reqlog.go:178`）生成并向 Context 注入 `slot := &errSlot{}`（使用私有 Context 键 `ctxKeyErrSlot{}`）。
- 任意 handler 出口通过 `recordError(r, err)` 直接向堆指针槽位写入 `slot.err = err`（同时对裸 handler 单测兼容回退到 Context 值拷贝 `errContextKey{}`）。
- 该堆指针机制从根本上消除了中间层如果执行 `r = r.WithContext(...)` 浅拷贝而导致外层中间件丢失 `rawErr` 的风险。

**中间件负责**：
1. 为**每个**请求生成/沿用 **request-id**（入：`X-Request-Id` 头，无则生成；出：写回响应头）。
2. 用 `log/slog`（与 `cmd/liquidator/main.go:29` 同一套结构化日志配置）记录一条 JSON：
   `{requestId, method, path, status, durationMs, err}`。
3. 在 `err` 字段里记 **raw error 的完整文本 + error 链**（`errors.Unwrap` 展开 `%w`）。
4. **在写入日志之前做脱敏**（见 §6 的负面后果与 SEC-P0-3）。

**中间件明确不负责**：
- **不读也不改响应体**。它看不到 body，也不尝试重写。
  **判据**：包装前后 body **逐字节相同**（§4.2 P4）。
- **不改状态码**。
- **不做分类**。分类是 handler/错误类型的责任（§3.5），中间件只负责"记下来"。

> **为什么把"不改响应体"写成硬约束**：一旦中间件开始改 body，它就必须**缓冲**整个 body，
> 于是流式响应、`204`、以及 `jsonResponse` 的多路径写入都会受影响，
> 而**"中间件把正确的 body 改坏"不会报错，只会让某个端点的返回变样**——
> 正是 D3 说的"失败即无声"。一条只写的中间件可以被逐字节判据钉死；一条会改的不能。

### 3.3 【裁定 3】向上游（= 调用方）抛出时，转化为业务语言

- **定义**：`error` 字段的内容必须是**该受众能懂且能据此行动**的表述。
  可操作性有两级，**都要能表达**：
  1. 调用方**能自己解决的** → 说清怎么解决（如"该标的无可用行情，请换一个代码"）。
  2. 调用方**不能解决的**（部署未配置、上游故障、5xx） → **明确说这不是他的问题**，
     并给一个有界的预期（如"请稍后重试"）或把他引向正确路径。
  > 第 2 级**同样是业务语言**。"这不是你能修的"本身是可行动信息——
  > 它阻止用户去改一个他改不了的东西，也阻止他把系统故障误报成自己的操作错误。
- **词表定稿结论**：
  `pm-spec-driver`（产品业务用词）与 `sec-auditor`（安全最小暴露）已完成成对互审与定稿，
  12 个稳定 `ErrorCode` 枚举及其唯一固定业务文案完全收敛（见 §3.6），
  彻底消除双处维护冲突（D4）。

### 3.4 【裁定 4】不允许将原始报错响应到前端

**禁止进入响应体的清单**（可机械判定，见 §4.2）：

| # | 禁止项 | 本仓现存的实例（实测） |
| --- | --- | --- |
| 1 | Go 栈帧特征（`goroutine `、`.go:NN`、包内函数名） | 无（未直接 `debug.Stack()`，但 `fmt.Errorf("...%w")` 链会把内部包名带进文本） |
| 2 | SQL / 约束名 / 驱动名 | `database/db.go:89`（DSN 解析原因）· GAP-61 的脱敏残余 |
| 3 | **DSN / 连接字符串** | `db.go:24,89` |
| 4 | **环境变量名**（非目标形态） | `router.go:122,127,150` · `middleware.go:77` · `alpaca_client.go:23` |
| 5 | 环境变量的**值** | 未见明文值（GAP-12 已清理默认值），但**不得回归** |
| 6 | 第三方响应原文 | `alpaca_client.go:192`（截断 256）· `price_oracle.go:209`（截断 512）· `router.go:519`（`ExecuteTrade` SEC-P0-2） |
| 7 | 文件路径 / 主机名 / 内网地址 / URL 查询凭证 | `developer/github.go` 相关路径、`GO_BACKEND_URL`、`health.go:311` 探针 Steam Key（SEC-P0-1） |

> **禁止的是"这些形态"，不是"这些字符串"**。判据取**闭集**（§4.2 P1）而非禁词表——
> 禁词表永远漏一项，而闭集对**未登记的字符串**无条件失败。

### 3.5 【派生】按路由类别定义「说给谁听」与安全基线

同一个后端有两种受众，必须严格划分受众视图边界（满足 GAP-74 解除条件 ①②③）：

| 类别 | 路由 | 受众 | 允许的内容与边界 |
| --- | --- | --- | --- |
| **调用方视图** | `/api/v1/market/*`、`/api/v1/agentcard/*`、`/api/v1/stripe/*`、`/api/v1/game/*`、`/api/v1/agent/*`、`/developer/*` 等所有业务路由 | 最终用户 / 第三方 Agent | 仅返回闭集错误信封 `{"error": "<固定文案>", "code": "<ErrorCode>", "requestId": "<reqID>"}`（以及 verifier 附加 `valid`/`scheme`、developer/agent 的兼容字段）。**严禁**出现 §3.4 七类禁入项中的任何技术细节 |
| **运营方视图** | `/healthz` · `/health` · `/api/v1/health` · `/api/v1/market/health` · `/api/v1/stats` | 部署者 / 运维 | **仅允许**返回配置缺失项的**环境变量名**（如 `"ALPACA_API_KEY, ALPACA_API_SECRET"`）及组件就绪布尔状态。**严禁**返回变量值、DSN、口令、未脱敏 URL 查询凭证或内部 panic 栈 |
| **仅日志** | 一切 | 事后排查者 | 完整 raw error + error 链 + request-id（在入日志前必须经脱敏处理） |

**安全审计新纳入 02 环必改的 3 个 P0 泄漏点**：
1. **`SEC-P0-1`（`health.go:311-315` & `:91,102`）**：`probeSteam` 请求 URL 含 `?key=<STEAM_API_KEY>`，网络层失败时 `*url.Error` 会将含明文 Key 的完整 URL 写进 `/healthz` 的 `probes.steam.error`。02 环必须在 `health.go` 的 `runProbe` 出口调用 `sanitizeLogValue` 并剥离 URL 查询参数，同时将 `:91` 的 `probe panicked: %v` 收敛为固定文案 `"probe panicked"`。
2. **`SEC-P0-2`（`router.go:519` & `:418`）**：`ExecuteTrade` 在 `HTTP 200 OK` 分支将含 Alpaca 256 字节响应原文的 `err.Error()` 赋给 `res.Message`。02 环必须在 `router.go:510-520` 当 `err != nil`（且非凭证缺失）时调用 `recordError(r, err)` 并将 `res.Message` 覆写为 `errorCopyFor(CodeUpstreamUnavailable)`。
3. **`SEC-P0-3`（`reqlog.go` 残余 #6 与反引号 DSN）**：在 `reqlog.go` 增补上游截断响应体前缀脱敏并拓宽 `reDSN` 前缀字符集（含反引号 `` ` `` 与引号）。

### 3.6 【派生】四类出口、12 个 ErrorCode 闭集与既有判据消解序列

#### 3.6.1 后端四类错误出口统一收口
实测盘点后端现存的 4 类错误暴露出口，02 环全部统一改造收敛：
- **出口 1：`jsonError`（共 51 处）**：`router.go` 47 处 + `middleware.go` 4 处（`:95,100,111,133`），统一替换为 `writeError(w, r, status, code, rawErr)`，写入信封并调用 `recordError`。
- **出口 2：手写 map（1 处）**：`router.go:670-675`（`verifier/verify`），调用 `recordError(r, err)` 并返回 `{"valid": false, "scheme": d.Verifier.Scheme(), "error": errorCopyFor(CodeInvalidProof), "code": "INVALID_PROOF", "requestId": reqID}`。
- **出口 3：`jsonEnvelope` 错误分支（12 处）**：`router.go:703-810`（其中 `:721,751,780,810` 4 处原拼接了 `err.Error()`），引入 `jsonEnvelopeError(w, r, httpStatus, codeInt, errCode, rawErr)`，输出 `{"code": codeInt, "response": string(errCode), "error": errorCopyFor(errCode), "errorCode": string(errCode), "requestId": reqID, "data": nil}`。
- **出口 4：结构体 200 OK 伪成功错误分支（1 处）**：`router.go:519`（`ExecuteTrade`），调用 `recordError(r, err)` 并将 `res.Message` 覆写为 `errorCopyFor(CodeUpstreamUnavailable)`。

#### 3.6.3 既有测试判据冲突消解序列（C1~C5）
为避免在加字段与改文案时造成既有测试断言冲突，02 环必须严格遵守"先改判据带负向对照、再改实现代码"的纪律：
- **C1 & C2（`market_test.go:182-184` & `market_edge_qa_test.go:186-188`）**：
  拒绝体顶层键严格断言从 `["error"]` 升级为 `["code", "error", "requestId"]`；必须附加负向对照测试（证明若响应体多出 `"price"`、`"data"` 等未预期键或数值时，`assertRefusal` 仍能捕获并失败）。
- **C3（`market_test.go:209-211`）**：
  调用方业务路由 `/api/v1/market/trade` 的 503 断言改为断言 `payload.Code == "SERVICE_NOT_CONFIGURED"` 且其文案与信封中**不含** `"ALPACA_API_KEY"`；运营方诊断路由 `/healthz` 与 `/api/v1/market/health` 保持现有断言不变（允许包含缺失的环境变量名 `"ALPACA_API_KEY"`）。

## 4. 可测的验收标准（01 环准出要求，D2）

> 全部为**性质断言**，不是清单比对；每条都给出**能红的形态**。
> 执行方式：`falsifier` / `gate-auditor` **只读无 shell**，命令**由总控代跑**后回灌 stdout
> （`AGENTS.md` §4.1）。

#### 4.1 正向判据

| # | 判据 | 命令（示意，02/03 环落地时固化） | 预期 |
| --- | --- | --- | --- |
| P1 | **闭集**：任一错误响应的 `error` 字段值，必须严格属于 12 个 `ErrorCode` 对应的固定业务文案闭集（§3.6.2） | `go test ./internal/httpapi/ -run TestErrorCopyIsClosedSet` | pass；**任何未登记字符串或拼接失败** |

### 4.2 负向证伪判据（D3，**必须真跑**）

| # | 注入 | 判据 |
| --- | --- | --- |
| N1 | **内部故障注入**：① DB 不可达 ② Alpaca 返回 500 且 body 为 `{"message":"...","code":40110000}` ③ 构造一个 `errors.New("pgx: SQLSTATE 23505 ...")` 的路径 | 响应体**不含** §3.4 清单任一形态；且 **P1 的闭集断言必须红**（若把原始报错塞回 `error`，P1 即失败） |
| N2 | **把中间件注释掉**（模拟"忘了接"） | **P2 必须红**（日志里没有 raw error）。若 P2 仍绿，说明它测的不是中间件 |
| N3 | **让词表缺一个 code** | **P1 必须红** |
| N4 | **让某个 code 无任何触发路径**（死分支） | **P3 必须红** |
| N5 | **在中间件里 `w.Write` 一个字节** | **P4 必须红** |

> **为什么 N1 单独不足以证明**：一个**把错误全吞掉**的实现（响应体为空、日志也不记）

> 这正是 `AGENTS.md` §8「只有 ② 仍有牙，才能反推 ① 的静默是确无判据」的同一条推理。

## 5. 替代方案（为何不取）

### 方案 A：本 ADR（后端统一 + 中间件留痕 + 业务语言）

**优点**：分类与文案有**唯一持有者**（D4）；泄漏可机械判定（闭集）；raw error 可排查（request-id 关联）。
**代价**：一次性迁移 51 个调用点与另外 3 类出口；需严格遵循 C1~C5 测试判据消解顺序（§3.6.3）。

### 方案 B：前端各自处理（**现状**）

- **不取**。理由不是"不好看"，而是**它已经产生了可测量的伤害**：
  前端**拿不到真因**（分类靠 HTTP 状态码猜，`api.ts:312-316`），
  于是 `503` 一律显示成"未配置"——**哪怕真实原因是上游故障**。
  这正是 issue #33 的现象。
- 并且它**结构性违反 D4**：业务语言在 `marketFeed.ts` 与后端各存一份，
  **改一处不改另一处不会有任何判据变红**。`marketFeed.ts:256` 与
  `router.go:150` 现在就在讲同一件事、用两种说法。

### 方案 C：后端逐 handler 手写文案，不引入分类与中间件

- **不取**。这是把现状的**形状**保留下来、只把**内容**改好：
  51 个调用点**没有收敛点**，新增一个 handler 会**静默**回到泄漏形态——
  无人会因为在 `router.go` 里新写一行 `jsonError(w, 500, err.Error())` 而收到任何提示。
- 与 `AGENTS.md` D3 同源：**"改了"与"守得住"是两件事**。

### 方案 D：后端只返回 `code`，全部文案放前端（i18n 友好）

- **部分可取，但不单独取**。剥掉 JSON 的场合它很常见，本仓却不适用：
  ① `error` 字段是可读字符串是**既有契约**（`api.ts:305`），改成纯 code 是**破坏性变更**；
  ② 它把"业务语言的成熟度"放回**前端**，与裁定 1 直接冲突；
  ③ **第三方 Agent 消费本 API**（`/api/v1/agent/*`），它们不共享前端的词表——
  一个只有 `code` 的响应会对它们不可读。
- **本 ADR 取折中**：后端给 `code` **和**业务语言，前端给渲染与本地化。
  这样 `code` 可供机器分支，`error` 可供人与 Agent 直读。

| 方案 | 分类收敛点 | raw error 去向 | 可机械判定 | 与判定 1 一致 |
| --- | --- | --- | --- | --- |
| **A 本 ADR** | **有**（中间件 + 分类枚举） | 日志 | ✅ 闭集 | ✅ |
| B 前端各自处理 | ❌ | 直接进响应体 | ❌ | ❌ |
| C 后端手写 | ❌（51 处） | 直接进响应体 | ❌ | 部分 |
| D 只给 code | 有 | 日志 | ✅ | ✅（但破坏既有契约 + Agent 不可读） |

## 6. 权衡与后果

### 正面

- **可排查**：每个响应带 `requestId`，日志里有完整 error 链 → 用户一句"报错码 xxx"即可定位。
  这是**当前完全没有的能力**（本仓 `backend/internal/httpapi/` 无任何 request-id / 结构化请求日志）。
- **可判定**：闭集判据把"有没有泄漏"从**人眼审查**变成**机械红绿**。
- **一次收口**：`router.go:150` 那类"文案里直写 env 变量名"的点，改完之后
  **结构上无法再出现**——因为词表里没有位置放它。
- **对外一致性**：`/api/v1/agent/*` 的第三方消费者拿到的是可读的 `error`，与前端同源。

### 负面 / 代价（**必须显式承认**）

1. **日志成为新的敏感面**。现状下，`db.go:89` 的 DSN 解析原因**可能**没被任何人记录；
   引入中间件后它**一定**会被写进日志。而本仓的脱敏本就不完整——
   **GAP-61**（`sanitizeDSNError` 按锚点替换，锚点之外的明文口令回显不被脱敏）。
   **故 GAP-74 的实现在写日志之前必须脱敏，且该脱敏的判据受 GAP-61 的既有缺口限制。**
   这不是"以后再说"：**中间件是一台把内部细节搬到磁盘上的机器**，
   它把 GAP-61 的暴露面从"可能"变成"必然"。
   → **GAP-74 的解除条件 ②**：已在 01 环审计出 `SEC-P0-3`，02 环拓宽脱敏正则与前缀，并在日志侧增补防泄漏判据。
2. **迁移是分批的，期间两套口径并存**。51 处调用点不会一天改完。
   与 D4「禁止两处不同成熟度的事实」直接冲突。
   **缓解建议**（交 02 环定）：先落**分类枚举 + 中间件 + 一条机械守卫**
   （对 `router.go` 里 `jsonError(w, ..., err.Error())` 的形态做静态断言 → 红），
   **新增代码立即受禁**，既有代码按端点分批迁移，并在台账里保持迁移进度可见。
   **不要**用一次巨型 PR 全量重写——那是 `docs/changes/020`（GAP-35）记录过的教训的同类：
   **把真改动埋在几千行噪声里，等于让评审失效**。
3. **`marketFeed.ts` 的 `FAILURE_COPY` 会与后端词表重复一段时间**。
   收缩它需要后端**先**能给出分类（当前只给状态码），否则前端无事可做。
   → 依赖顺序不可颠倒：**后端先给 `code`，前端后收缩**。
4. **§3.6 的 `market_test.go:182-184` 会先红**。按 C1~C5 既定顺序消解：
   **必须先改判据带负向对照、再改实现**。

### 遗留与定稿状态（满足 GAP-74 解除条件 ①②③）

| 项 | 归属 / 状态 |
| --- | --- |
| 词表定稿（业务语言用词 + `code` 枚举 + 禁入清单） | ✅ **已定稿**：12 个 `ErrorCode` 闭集与固定文案已完全收敛（见 §3.6.2） |

## 8. 实施依赖顺序（不可颠倒）

```
01 设计环（本 ADR）
   └─ 产出：决策 1~4 + 受众分类 + 信封 + 12 闭集词表 + *errSlot 机制 + C1~C5 判据序列 + 成对互审定稿
        │
        ▼
02 开发环
   ├─ ① 测试判据冲突消解（C1~C5，先改断言带负向对照）
   ├─ ② 中间件（*errSlot 槽位 + 只写日志 + request-id + 增强脱敏；不改响应体）
   ├─ ③ 修复 3 个 P0 泄漏点（SEC-P0-1 探针 URL 脱敏、SEC-P0-2 覆写、SEC-P0-3 正则拓展）
   ├─ ④ 统一四类错误出口（51 处 writeError + 12 处 jsonEnvelopeError + 1 处 verifier + 1 处 trade）
   └─ ⑤ 前端词表收缩（FAILURE_COPY 收缩为按 code 查表渲染）
        │
        ▼
03 测试环
   ├─ 正向 P1~P5
   └─ 负向 N1~N5（其中 N1「故障不得泄漏到响应体」是驳回本 ADR 的那条）
```

**顺序颠倒的后果**：
- 先收缩前端词表、后端还没给 `code` → 前端**无事可做**，只能继续用状态码猜（回到方案 B）。
- 先加 `code`、后改 `market_test.go:182-184` → 实现方撞红，**可能**顺手把那条判据删掉
  （"判据消失"而非"判据更新"，正是 §6 负面后果 4 要防的）。
- 先迁移端点、后建词表 → 每个端点自己写文案，**重现方案 C**。
