## 1. 真实门控在哪（先定位，再动手）

issue 指了三个文件，但**没有一条代码路径写着「必须先登录 Google」**——实测是这样：

| 候选 | 实测 | 证据（改前行号） |
| --- | --- | --- |
| 组件级守卫「账户中心要先登录」？ | **不存在**。账户面板是 `<button onClick={() => setDropdownOpen(true)}>` 直接开，无任何前置条件 | `NavAuthBadges.tsx:271` |
| 路由级守卫 / 重定向到 `/login`？ | **不存在**。全仓 `git grep` 无 `login` 路由、无 `redirect(` | `src/app/**` 无 `login/page.tsx` |
| `GoogleAuthWall` 是门？ | **不是**。它只挂在 `/agentcard` 的 **Google 标签页**里，是**信用增强**而不是入口 | `AgentCardTerminal.tsx:556` |
| **真实形态** | **账户面板里唯一的「连接钱包」按钮，回调就是页面级的 `authLogin()`**——即 `login()` **全量方法表**（`["wallet","google","github","email"]`）。同一面板里**唯一带「钱包」语义的 Privy hook（`linkWallet`）是会话后才出现的** | 改前 `NavAuthBadges.tsx:478-487` → `onConnectWallet` → `app/page.tsx:169-186` `authLogin()`；Provider 配置 `Providers.tsx:161`；`linkWallet` 条件 `NavAuthBadges.tsx:458` |

**结论**：这是一条**「入口只有一个、且它不自称是钱包入口」**的缺陷，**不是**任何一条
「if (!google) return」式的硬门控。所以 issue 的措辞（"必须先 Google"）描述的是**体验事实**：
纯钱包用户在面板里点「Connect Wallet」，拿到的是与所有人同一个模态，
而他唯一**被明确承诺**的东西（钱包）在 UI 上没有被单独承诺；
面板里的 Google 行写着 `+$1,200 USD`、GitHub 行 `+$1,000 USD`，
**强化了"钱包只是配菜、Google 才是主菜"的读法**。

> **本节的意义**：**没有硬门控**这件事本身要写下来。否则修法会去找一个不存在的 `if`，
> 或者更糟——**凭空加一个"允许 Google 缺席"的开关**，去堵一条从来没堵过的路（D1：读到才算）。

## 2. 修法（选「钱包成为独立入口」，不选「启用 Privy 钱包登录」）

**先查 Privy SDK 的真实 API**（`node_modules/@privy-io/react-auth/dist/dts/index.d.ts:743-800`）：

| Hook | 官方 JSDoc 原文 | 含义 |
| --- | --- | --- |
| `login(options?)` | *"Opens the Privy login modal and prompts the user to login."*<br>`options.loginMethods`: *"custom login methods to display in the login modal. This will overwrite the value provider to the client config."* | **可运行时收窄方法表** |
| `linkWallet(options?)` | *"**For users who are authenticated**, opens the Privy modal and prompts the user to link a wallet."* | **不是登录入口** |
| `connectWallet(options?)` | *"Opens the Privy modal and prompts the user to connect a wallet."*（无 "For users who are authenticated" 限定） | 语义**在本包类型里不可判** |

**因此**：
1. **`linkWallet` 不能用来「先连钱包」**——它自己写着要已认证。改前把它摆在唯一位置，
   正是「点了没反应」那种失败。
2. **备选路径（`connectWallet`）不采**：它的语义只由**本仓无法读到**的上游文档裁决，
   而 `.claude` 口径是「**名字写错**与**能力缺失**在观测上不可分」（`AGENTS.md` §8）。
   在一条**猜错的代价是登录坏掉**的路径上，选**唯一有类型/JSDoc 双证据**的那条。
3. **采用**：`login(WALLET_ONLY_LOGIN_OPTIONS)`——钱包轨**独立且先出现**，
   Google/GitHub 仍是同一模态里可继续走的方法（**一条轨都没删**，Trust/Identity 支柱不动）。

### 2.1 一处副产品（顺手修掉的**真**缺陷）

把 `login` 的签名从 `() => void` 放宽为 `(options?) => void` 后，`tsc` 立刻报出：

```
src/components/DeveloperConsole.tsx(679,17): error TS2322: Type '(options?: WalletOnlyLoginOptions | undefined) => void'
  is not assignable to type 'MouseEventHandler<HTMLButtonElement>'.
```

即 `onClick={authLogin}` **把 React 的点击事件当成 options 交给了 SDK**。
改前因为签名是零参，这个错误**被类型系统挡住看不见**；一旦签名变宽，它就是**活的**。
两处（`:679` / `:1020`）改为 `() => authLogin()`。

### 2.2 一处**我自己引入又修掉**的回归（留档，`AGENTS.md` §9 体例）

第一版把「连接钱包」按钮的条件写成 `walletRail !== "none"`，而当时的 dispatch 把
**未启用 Privy** 也判成 `none`。后果：**无 `NEXT_PUBLIC_PRIVY_APP_ID` 的本地开发/无 Privy 部署里，
钱包按钮会整个消失**——`Providers` 的 fallback 分支本来是靠这个按钮走注入式钱包连接的。
**这与 #30 是同一类缺陷，只是换了一支 Provider。** 修法：dispatch **不再吃 `isPrivyEnabled`**
（两支都能开会话），Provider 模式只决定**传给 `login` 的参数**
（`walletSessionLoginOptions`：Privy 给覆盖对象，fallback 给 `undefined`）。
`tests/wallet-login.test.ts` 里有一条用例专门守这一点。

## 6. 与 PR #37（`fix/login-state-sync`）的冲突面

**语义上互不矛盾**：#37 解决的是「登录态在组件间不同步、登出粘住」（一个 `authState` SSOT）；

wallet-only 分支**（`fix/login-state-sync:src/components/NavAuthBadges.tsx`），即
**#37 假定"钱包登录会存在"**——本改动正是把那个前提补上。两者是互补关系，不是竞争关系。

**合并建议**（留给合并方）：先合 #37，再把本改动的
`resolveWalletRailAction` / `walletSessionLoginOptions` **接到 #37 的 `authState` 上**
（该 dispatch 的输入只有 `authenticated` 与 `hasLinkWallet`，与 #37 的 SSOT 无耦合，
