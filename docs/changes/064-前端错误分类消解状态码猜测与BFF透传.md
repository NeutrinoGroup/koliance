## 1. 改动背景与目标

在既有架构中，前端对后端响应的失败原因存在依赖 HTTP 状态码盲猜的问题（GAP 台账 / ADR-006 §3.6 / issue #33）：
- 只要上游返回 503，前端 `classifyStatus` 便一律归类为 `"not-configured"`（判定为未配置 ALPACA_API_KEY 凭据），导致数据库不可用等非凭据故障被误报；
- `/api/market` BFF 路由对非 404 的上游错误一律强制覆盖为 503（`status = upstream.status === 404 ? 404 : 503`），抹杀了上游原本返回的 500/502/429 等状态。

本改动针对上述问题执行彻底消解与收敛：
1. **优先 ADR-006 ErrorCode 分类**：`classifyStatus` 优先根据后端返回的标准错误信封中的 `code` 判断分类，而非仅凭 `status === 503` 猜测。
2. **DATABASE_UNAVAILABLE 精确分类**：若 `code === "DATABASE_UNAVAILABLE"`，不能猜成 `"not-configured"`，正确归类为 `"upstream-error"` 并保留其精确 `detail` 与 `code`。
3. **BFF 代理状态码保真透传**：`src/app/api/market/route.ts` 保持 upstream 的原始 HTTP status 透传（如 500/502/429 等），消除一律覆盖为 503 的强转逻辑。
4. **测试断言校准与扩充**：校准既有测试中对强转 503 的残留假定，并新增针对 `classifyStatus`、`fetchMarketOverviewChecked` 与 BFF 透传的完整测试，确保断言全绿。

## 2. 详细实现清单与设计决策

### 2.1 `src/lib/api.ts`
- **重构并导出 `classifyStatus`**：
  ```ts
  export function classifyStatus(
    status: number,
    detail: string,
    envelope?: ApiErrorEnvelope | { code?: string }
  ): { reason: MarketFetchReason; detail: string } {
    const code = envelope?.code;

    if (code) {
      if (code === "SERVICE_NOT_CONFIGURED") {
        return { reason: "not-configured", detail };
      }
      if (
        code === "DATABASE_UNAVAILABLE" ||
        code === "UPSTREAM_UNAVAILABLE" ||
        code === "INTERNAL_ERROR" ||
        code === "RATE_LIMITED"
      ) {
        return { reason: "upstream-error", detail };
      }
      if (code === "RESOURCE_NOT_FOUND") {
        return { reason: "invalid-symbol", detail };
      }
      if (status === 503) {
        return { reason: "upstream-error", detail };
      }
    }

    if (status === 503) {
      if (detail && detail.toLowerCase().includes("database")) {
        return { reason: "upstream-error", detail };
      }
      return { reason: "not-configured", detail };
    }
    if (status === 404) return { reason: "invalid-symbol", detail };
    return { reason: "upstream-error", detail };
  }
  ```
- **改造 `marketGet` 消费处**：
  解析 ADR-006 信封 `env` 后，将 `env` 作为第三个参数传入 `classifyStatus(res.status, detail, env)`，返回对象中保留 `classified.reason`、`classified.detail`、`env.code` 与 `env.requestId`。

### 2.2 `src/app/api/market/route.ts`
- 从 `@/lib/api` 导入 `classifyStatus`，实现 BFF 层与前端客户端共用同一分类判定单一事实源（D4）。
- 在 upstream 报错分支中：
  - 提取 `code` 与 `requestId`；
  - 经 `classifyStatus(upstream.status, detail, { code, error: detail, requestId })` 判定 `reason`（`DATABASE_UNAVAILABLE` 归为 `upstream-error`）；
  - 保留原始 `upstream.status` 透传至 `refuse(status, reason, detail, { symbol, code, requestId })`。

### 2.3 测试套件更新与补齐
- **`tests/api-error-envelope.test.ts`**：
  - 增加 `classifyStatus` 单元测试组（6 项）：覆盖 `DATABASE_UNAVAILABLE` 优先、`SERVICE_NOT_CONFIGURED`、`UPSTREAM_UNAVAILABLE`、`RESOURCE_NOT_FOUND` 以及无 code 场景的关键词兜底与未配置兜底；
  - 增加 `fetchMarketOverviewChecked` 针对 503 `DATABASE_UNAVAILABLE` 返回 `upstream-error` 的断言；
  - 增加 `/api/market BFF proxy route` 针对 503 `DATABASE_UNAVAILABLE` 返回 `upstream-error`、500 `INTERNAL_ERROR` 原始状态保留、502 `UPSTREAM_UNAVAILABLE` 原始状态保留、429 `RATE_LIMITED` 原始状态保留的端到端测试。
- **`tests/market-route.test.ts`**：
  - 校准 `relays 502 as upstream-error` 用例：断言 `res.status` 为 502（此前硬编码断言 503）。
- **`tests/market-independence.test.ts`**：
  - 校准网关 500 测试用例：`wantStatus` 由 `[503]` 调整为 `[500]`。
- **`tests/api-key-db.test.ts`**：
  - 为异步网络用例补充 15000ms 超时参数，与 `console-api-keys-route.test.ts` 保持一致，消除高并发用例争抢时的超时抖动。
