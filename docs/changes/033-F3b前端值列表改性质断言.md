## 1. 缺陷（`docs/changes/029` §3 行 F3b 的复述，非本记录新发现）

`tests/market-no-synthetic.test.ts` 的「前端不得有硬编码行情」判据是一张**值列表**：

```ts
const FABRICATED_VALUES = ['"100,000.00"', '"400,000.00"', '"100000.00"', '"400000.00"',
                           "142.8", "234.5", "258.4", "65420", "2640.5"];
// …for (const value of FABRICATED_VALUES) expect(source).not.toContain(value);
```

**列表只能抓到列表上的字符串**。`qa-validator` 往 `MarketTerminal.tsx` 注回**表上没有**的值
`"98500.00"` / `"ord_seed_first"` / `"+7.25%"`，本文件 **13/13 全绿**；本次**原样复现**（§3）。

**这不是第一次**：`028` §4.4 的 F4b 记录过同一形态——第一版列表只有千分位写法 `"100,000.00"`，
注入用的是 `"100000.00"`，**守卫没抓到**。事后是把那一个值补进列表解决的。
同一判据以同一种方式失效两次，说明失效的**不是列表的内容，而是列表这一形式**；
再补一次值，只是把洞挪到下一个值上。

## 2. 改法：值列表 → 六条**性质**（在解析后的 AST 上判定）

判据的问题从「**这个字符串在不在表上**」改为「**这个东西像不像一条行情事实**」。
`scan()` 是**同一个谓词**，既跑真实源码也跑 §3 的注入源码——若负向对照另写一份拷贝，
它证明的只是那份拷贝。

| # | 性质 | 判定 | 抓到的旧向量 |
| --- | --- | --- | --- |
| 1 | `market-number` | 字符串/模板字面量/JSX 文本，**整串**是一个「行情量级」的数 | `98500.00` `+7.25%` `142.8` `65420` `$234.00` `100,000.00` |
| 2 | `fabrication-name` | 标识符/成员名含 `fallback`/`seed(ed)`/`tape`/`hardcod`/`pretend`/`fabricat` | `FALLBACK_MARKET_DATA` `seededRandom` `TICKER_TAPE` |
| 3 | `foreign-source-name` | 整串是 `snake_case` 字面量（**数据源名的形状**） | `ord_seed_first` `synthetic_curated` `synthetic_fallback` `monad_oracle_gatekeeper` `cached_calibrated_mirror` |
| 4 | `minted-order-id` | 整串以 `ord_`/`fill_`/`trade_`… 开头且**后面还有字面量片段** | `ord_seed_first` `ord_init_aapl` |
| 5 | `legal-entity` | 串内出现法人后缀（`Inc.` / `Corporation` / `LLC`…） | `NVIDIA Corporation` `Apple Inc.` |
| 6 | `reported-fact-attribute` | **JSX 属性名**像一条被报告的事实（`value`/`price`/`cash`…）且其值是**写死的数字** | `<MetricCell value="98500.00" />` |

### 2.1 为什么 1 号性质要带阈值（以及阈值是怎么定的）

本文件守的表面里有一个 **Tailwind + SVG 组件**，里面**合法地**写着 `"0.25"`（透明度）、
`"100%"`（渐变停靠点）、`"2.5"`（描边宽度）。**实测**：松口径（`\d+\.\d+` 或 5 位整数）
在 `MarketTerminal.tsx` 上命中 **30 条 class 串 + 5 个 SVG 属性**——
一个对 `stopOpacity="0.25"` 报警的守卫，**下场是被删掉**，所以阈值是判据的一部分而非修饰：

| 量级标记 | 例 | 为什么几何常量不是这样写 |
| --- | --- | --- |
| 有符号 | `+7.25%` `-3.14` | 涨跌幅有正负；`offset`/`stopOpacity` 永远不带符号 |
| 带 `$` | `$234.00` | 只可能是钱 |
| 千分位 | `100,000.00` | 人写的金额 |
| ≥2 位整数带小数 | `142.8` `98500.00` | `0.25` 只有 1 位整数 |
| ≥4 位整数 | `65420` `10000` | `0`/`1`/`100` 不是行情数字 |

**刻意不算**：`0` `1` `2.5` `0.25` `0.0` `0%` `100%`。

### 2.2 **实测**逼出来的两处修正（不是设计时的推断）

写完后**第一次真跑**就红了两条，两处都是真实假阳性/真漏判，已修，证据见 §3：

1. **`"7999"` —— AgentCard 的 MCC 码。**
   `src/lib/api.ts:264` 的 `authorizeMicropayment(... mcc: string = "7999")` 是 **ISO 18245 商户类别码**，
   一个 4 位整数，被「≥4 位整数」口径命中。原判据对 `lib/api.ts` 是**只剥注释、扫全文**
   （仅 `Math.random()` 那条按 MARKET banner 分节）。
   **改法**：`lib/api.ts` **按 MARKET banner 分节**——节外**填空格（不裁剪）**，故偏移与行号仍指向真实文件；
   另三个文件是行情专属，仍全文扫。节外被排除的两处**都是实测的**：`authorizeMicropayment` 的 `"7999"`、
   `generateDeveloperProof` 的 `Math.random()`。
2. **`Apple Inc.` —— `\b` 匹配不上。**
   `LEGAL_ENTITY` 原用 `\b(?:Inc\.|…)\b`。`Inc.` 结尾是**点号**，点号后接的是串尾——
   **`\b` 在此永不成立**，于是「为 `Apple Inc.` 而写的规则认不出 `Apple Inc.`」。
   是 §4 那条**穷举旧向量**的负向对照把它抓出来的，不是读代码看出来的。
   **改法**：定界符改为 `(?:^|[^\w])` … `(?=$|[^\w])`。

## 5. 判据的**边界**（如实标注，不夸大）

1. **写不进去的形态**：性质扫描判的是**整条字面量**与**空格分隔的邻接**，不是「句子中间的数字」。
   把一个编造的行情**写进一句更长的文案里**（`"当前价 98500.00 美元"`）不会被抓到。
   —— 本缺陷在本表面的**每一次**发生都是数据结构/state 初值里的**整条字面量**，但这是**残留风险**，不是「等价强度」。
2. **`Monad Ecosystem Token` 只剩字面钉子**：它**没有法人后缀**，`legal-entity` 认不出。
   最自然的推广「两个以上首字母大写的单词」**实测会误报**本表面的正常文案
   （`"Alpaca Daily Bars Tape"`、`"Loading Chart Data..."`），故**未纳入**，只保留字面钉子。
   这条边界**写进了用例断言**（`expect(LEGAL_ENTITY.test("Monad Ecosystem Token (Parallel EVM)")).toBe(false)`），
   以免将来被误当成「已覆盖」。
3. **`lib/api.ts` 只扫 MARKET 节**：节外新增的假行情不会被抓。这是**刻意的取舍**——
   全文扫会把 MCC 码 `"7999"` 判成行情数字（§2.2 实测）。该文件节外是 Steam/AgentCard/Stripe/GitHub 适配器。
4. **仍不是「渲染层」判据**：本文件是**源文本**判据，与行为判据是两回事；
   `vitest.config.mts` 是 `environment: "node"`，组件从不渲染。真正的渲染层覆盖需要 e2e
   （`028` §4.5 / `029` §6 同口径：**未跑**）。

## 5.5 一次**未归属**的全套抖动（如实记录，未修）

改动后的全套共跑 **5 次：4 绿 1 红**。那一次红**不在本文件的表面**：

```
FAIL  tests/console-api-keys-route.test.ts > … > creates user API key and saves into api_keys table …
Error: Test timed out in 5000ms.
FAIL  tests/console-api-keys-route.test.ts > … > lists API keys for authenticated registered developer
AssertionError: expected 0 to be greater than 0
 Test Files  1 failed | 19 passed (20)
      Tests  2 failed | 193 passed (195)
VITEST_EXIT=1
```

**证据与判断**：

- 该文件**单跑两次全绿**（`4 passed (4)`，`EXIT=0` ×2）；随后**全套连跑两次全绿**
  （`20 passed / 195 passed`，`EXIT=0` ×2）。故它是**抖动**，不是稳定失败。
- **本变更未触碰它**，也未触碰它依赖的任何生产代码（§2.3、§5 已列明本变更只改一个测试文件）。
- **一个诱因在写记录前被自己否掉了，一并留痕**：本文件新增了 `import ts from "typescript"`，
  最初怀疑是「解析成本把全套拖慢、进而把一条 5000ms 超时用例推过界」。**实测数据不支持它**——
  五次全套的 `import` 阶段读数为 `22.04s`（基线）/ `22.98s` / **`22.29s`（红的那次）** /
  `28.64s` / `23.69s`：**红的那次 import 是正常的**，而 import 最慢的那次（28.64s）反而全绿。
  故该假设**不成立**，不作为解释留下。
- **因此本记录对该抖动只陈述两条事实**：① 它是**非稳定**的（单跑 ×2 绿、全套 ×2 绿）；
  ② 它**不在**本变更的表面上。**根因未定，如实标注为未知**，不做因果宣称。
- **未修**：该用例属 `console` 面，不在 F3b 的任务域内；在没有隔离实验前动它，
  就是「把一次抖动当成缺陷」——与「把子串表当成性质」是同一类错误。
  **建议**（不在本次范围）：由 `qa-validator` 在 `console-api-keys-route.test.ts` 上跑
  5 次连跑定抖动率，再决定是调超时、还是去查共享可变状态 / 并发下的 RLS 桩。
