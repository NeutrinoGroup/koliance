## 1. 缺口

03 环准出有两句：**新用例 100% 纳入 CI 矩阵** + **覆盖率配置阈值**。
后者在合约侧（`docs/changes/007`，GAP-32）与前端侧（`docs/changes/011`，GAP-33）都已落地，
**后端侧一直是空的**。后端 `.github/workflows/ci.yml` 的 `backend` job 只跑
`go build` / `go vet` / `go test -race`——**Go 报覆盖率，但没有阈值**：
`go test -cover` 在任何百分比上都 `exit 0`，所以一个覆盖率大幅下滑的改动**会静默通过 CI**。

## 2. 范围：为什么只门禁 15 / 23 个包

先量再说。`go test -count=1 -covermode=atomic -coverprofile=... ./...` 后
用 `go tool cover -func` 与逐包 `go test -cover` **两条独立路径**对拍，读到：

| 包 | 语句 | 读数 | 处置 |
| --- | --- | --- | --- |
| `cmd/api` `cmd/liquidator` `cmd/migrate` | 41+46+46 | **0.0%** | **排除**——`main` 装配 |
| `internal/chain/bindings` | 471 | **0.0%** | **排除**——abigen 生成物 |
| `internal/developer` | 61 | **0.0%** | **排除**——无测试文件 |
| `internal/liquidation` | 42 | **0.0%** | **排除**——**有测试文件却仍是 0%**，登记 **GAP-72** |
| `internal/platform/stripeclient` | 12 | **0.0%** | **排除**——无测试文件 |
| `internal/model` | 0 | n/a | **排除**——纯类型文件，profile 里**零语句块** |
| 其余 **15 个包** | **2435** | **71.99%** | **门禁** |

### 2.1 不门禁全树的理由（不是"数字难看"，是"门禁会失效"）

全树读数（`go tool cover -func`）：**55.6%**，分母 3154。被排除的 **719 条语句**（23%）
全是**公认没有测试**的代码——`cmd/*` 的 main、abigen 生成物、无测试的四包。
门禁一个**含 0% 包的总数**，等于把地板定在这些 0% 包之上：**它永远不会为正确的原因移动**。

这与前端 `docs/changes/011` 记录的**同一个陷阱**同构（不加 `include` 时 v8 报 70.35%，
但那 70.35% 只统计"被测试 import 过"的文件，新增无人 import 的组件一点都不会降）。
**两侧的解法也一样：选范围，不是选一个更小的数字。**

### 2.2 排除 ≠ 宣布它们没问题

八个被排除的包**一个都没被宣布为"没问题"**：三类是**生成物 / 进程装配**（本就不该门禁），
四类是**没有测试**——已按项目规矩**登记为带编号的缺口**，不是"平均进去算了"。
排除一个包、同时让它在无人测量中腐烂，是比这更贵的错误。

**一律取实测下方 3~6 点**，理由逐字沿自 `007`（那个数字是它自己的首次 CI 失败换来的）：

> 贴着实测值定的地板，会在下一次无关重构时变红，然后被赶时间的人删掉；低几点仍能抓住真实下滑。

### 3.2 为什么**同时**要总数地板（这里是算出来的，不是偏好）

门禁集 2435 条语句，其中 `httpapi` 一个包就 **604** 条。
**只门禁总数**的话，任何低于 `604/2435 = 24.8%` 的包**整个归零**都能通过
（损失 ≤ 24.8%，而总数余量 2.99 点）——`liquidator` 326 条语句全删掉只让总数掉 **5.83 点**，
**刚刚好**越过 2.99 点余量。这不是设计，是权重的巧合：包再小一点就变绿。

所以**逐包地板是"规则本身"**。

### 3.3 总数地板：**第一次取的值是死代码**

总数地板初稿取 **67.0**。落笔前做了一次「这条判据可能触发吗」的算术复核：

> **每个包都恰好坐在自己地板上**时，总数是 **67.61%**。

即：**逐包地板已经蕴含了 67.61%**，`totalFloor = 67.0` **永远不可能是那个让构建变红的原因**。
它不是第二道防线，是第二道**从不触发的**防线——**买的是虚假的安全感**。

这与本门禁自己要防的「空分母被当成 100%」**同族**：
**一个不可能失败的判据，与一个从未需要失败的判据，在观测上完全一致。**
报告不会显示它、任何测试也不会显示它——数字看起来合理、表格照样打印、门禁照样绿。

故总数地板定为 **69.0**（实测 71.99 下方 2.99 点，逐包地板蕴含值 67.61 上方 1.39 点），
并把这两条不等式变成**机械判据** `TestTotalFloorCanStillFire`（见 §4.3 N-5）。

**N-1a 是本任务要的那个**：**删掉一个用例 → 门禁变红**。
**N-1b 是它的加强版**：不作弊于"删测试"，而是**新增没人测的代码**——
这正是覆盖率门禁区别于"测试数量门禁"的地方。

**N-1b 顺带量出了本门禁的敏感度**（这比"它红了"更有用）：

- 给 `game`（207 条语句、地板 46）加 **10 条**未覆盖语句 → **47.93%，仍绿**；
- 加 **40 条** → **42.11%，变红**。

即 **`game` 的 4.24 点余量 ≈ 9 条语句**。**余量就是敏感度**，
这也把 §3.1 那句「低几点仍能抓住真实下滑」从口号变成了**可复算的数**。

**N-3 三条**（本仓**已经真发生过**的那一类——合约侧脚本在无分支数据的报告上打印
`branches 100.00%`，空分母被当成 100%，见 `AGENTS.md` §8）：

| 注入 | 实测 stderr | exit |
| --- | --- | --- |
| profile 文件不存在 | `no coverage report at coverage/coverage.out` + 给出生成命令 | 1 |
| profile 存在但无记录 | `profile coverage/coverage.out carries no coverage records` | 1 |
| profile 畸形 | `parse coverage/coverage.out: line 2: bad count "line": strconv.ParseInt: ...` | 1 |

三者都**不许**「没东西可测 = 过」。

> **上一条与 `AGENTS.md` §8 的「空分母」同族**：两者都是**解析器静默数错**。
> 临时采集脚本若按"连续空格"切分 profile 行，对只含单空格的行会**把块位置读成语句数**。
> 门禁实现从**右往左**切分，并有 `TestParseProfileSplitsCountsFromTheRight` 钉住。
> 这条不是假想：本次任务中**我自己写的第一版采集脚本就踩了它**，
> 并据此产出过一组**看起来自洽**的错误读数（详见 §6 末的更正留痕）。
