## 1. F5 · 「§4.3 结构面修复」没有任何判据绑到组件上（P1）

### 1.1 机制：修的是**一条产品路径的守卫**，而判据只覆盖了它调用的纯函数

`050` 的 §4.3 修复分两层（`docs/changes/050` §2.2）：

| 层 | 是什么 | 判据（`050` 给的） |
| --- | --- | --- |
| 结构面 | `NavAuthBadges` 的 bridge 守卫改用 `googleRowKey(storedGoogleRow())`，即**比对存进去的那一行** | 无 |
| 机制面 | `writeAccountState` 的写入幂等（同字节不写、不发事件） | 有（3 例，变异会红） |

`050` 给的三条键用例（`gives the exchange route's row and a re-spelled row the same key` 等）测的是
**`googleRowKey` 这个函数**。函数本身一直存在、一直正确——所以**把组件里的守卫整条换回改前形态**：

```ts
const stored = state.google;
if (stored && stored.id === `did:koliance:google:${privyUser.google?.subject}`) return;
```

**全套仍然全绿**（F5 由总控实测；**本轮在本仓内复现过，见 §4.1 的 A0**）。
这不是"少写了一条测试"，而是
**一个没有被任何判据绑住的产品修复**：它可以被下次重构原样改回去，而全套测试一声不响。
D3 的口径是**判据必须可证伪**——一条"改回去也不会红"的修复，其状态与**未修复**在观测上不可分。

> **它与 `050` §2.3 记录的那次诚实记录同族**：那一次是"`googleRowKey` 的 key 顺序**第一次变异时不可证伪**"，
> 这一次是"**组件有没有调用它**不可证伪"。两次都是**判据对着实现写，而不是对着真实形态写**。

### 1.2 修法：把守卫**绑到组件**（源级机械守卫，不需要 jsdom）

`tests/auth-state.test.ts` 新增一组 `the bridge recognises the stored row the way the store spells it`，
对 `NavAuthBadges.tsx` 的**源码**断言三件事：

| 用例 | 断言 | 为什么是这一条 |
| --- | --- | --- |
| `compares a key taken off the stored row, not the account it is about to write` | 那条比较语句里出现 `storedGoogleRow(` 与 `googleRowKey(`，且**不得**出现 `.id`；同时断言 `return` 确实由这个比较决定 | 正向是修复的形态，**负向就是 F5 的回归本身** |
| `writes a row that already agrees with the key it was recognised by` | 写出去的那一行**不带**第二个身份字段（`id:`），身份只由 `googleId: privyUser.google.subject` 表达 | 守卫按 `googleId` 取键、写入却带一个可能不一致的 `id`，就是 §4.3 的环换了个方向 |
| `has teeth on a commented-out guard` | 注释剥离器的**负向控制** | 见 §1.3 |

**比 `050` 的写法强在哪（这三点都是 F5 直接要求的）**：

1. **它读的是"哪两个东西在被比较"，而不是"某个名字有没有出现"**。比较语句用
   `effect.split(";").find((s) => s.includes("googleRowKey("))` **按内容**取出，不按变量名——
   把 `alreadyStored` 改名不会让守卫失效。反之，把 `googleRowKey(storedGoogleRow())` 换成任何
   **产生同一个值但方向错误**的写法（`stored.id` 直比），语句里就没有 `googleRowKey(`，**红**。
2. **它同时断言"由这个比较决定要不要 return"**：否则计算出来的键被丢掉也算"有 `googleRowKey`"。
   取键语句绑定的名字被读出后，用同一个名字构造 `if (name) return;`，不是硬编码某个变量名。
3. **它有自检**：窗口由 `const [signingOut, setSigningOut]` 到 `[privyUser, state.google, signingOut]`
   划定，并断言窗口内含 `privyUser?.google`。窗口取错时**先红**，而不是"没扫到任何东西"地通过——
   即本仓记过两次的**空分母**形态。

### 1.3 防注释伪造：`codeWindow` 剥注释，且**负向控制证明它真的在剥**

falsifier 指出的夹缝是：**源级断言读的是文本，所以"加一行注释"可以顶替被删掉的代码**
（既有守卫 `expect(source).toMatch(/if \(signingOut\) return;/)` 就有这个缝）。

本轮把三处源级断言（Sign Out 顺序、Sign In 顺序、bridge 守卫）**统一走 `codeWindow()`**：
它先剥 `//` 与 `/* */` 注释，再让断言去读。于是：

- 把守卫注释掉、逻辑改回 `stored.id` 直比 → **仍然红**（变异 A2 实测，见 §4）；
- 已存在的 `expect(source).toMatch(/Bridge the Privy user/)` 那一条**刻意保留读原文**——
  它要找的标记本来就在注释里，剥注释会让它必然失败。此处在用例里**写明**了原因，
  而不是悄悄改掉一个会变红的断言。

`has teeth on a commented-out guard` 是 `codeWindow` 的**负向控制**，四条一起跑：

| 断言 | 防的是什么 |
| --- | --- |
| `// if (googleRowKey(...)) { return; }` 剥后**不含** `googleRowKey(` | 注释顶替代码 |
| `/* stored.id === ... */` 剥后**不含** `stored.id` | 块注释是第二个藏身处 |
| `const u = "https://example.com/x"; const y = 1;` **含** `const y = 1;` | 剥注释器把 URL 里的 `//` 当注释，**吃掉整行**——那会让上面两条守卫开始对着"不存在的代码"通过 |

> **诚实标注**：`codeWindow` 是**手写扫描器**（跳字符串/模板串），不是真解析器。
> 一个含 `//` 的**正则字面量**仍可能让它误判；本轮断言的三个源文件里没有这种写法。
> 这是**结构性判据的已知边界**，不是"已解决"。

## 2. F7 · 点「解除」解除不掉：unlink 不经闸门（P2，与 F1 同族）

### 2.1 机制（读源码得出）

改前的 `NavAuthBadges.tsx:592` 是 `onClick={() => unlink("google")}`，而 `unlink` 的实现是

```ts
const unlink = useCallback((rail) => { writeAccountState(rail, null); }, []);
```

于是这条用户路径与 F1（Sign Out）**是同一个形状**，只是没走同一个闸门：

| # | 事实 | 处 |
| --- | --- | --- |
| 1 | `unlink("google")` 把 `koliance_google_profile` 删掉，发一次事件 | `KolianceAuthProvider.tsx:83-85` |
| 2 | `KolianceAuthProvider` 收到事件 → `setState` → `state.google` 由非空变 `null` | `KolianceAuthProvider.tsx:75` |
| 3 | bridge effect 的依赖含 `state.google` → **effect 重跑** | `NavAuthBadges.tsx` 的 bridge |
| 4 | 此刻 `privyUser.google` 仍非空（**解除本地行并不结束 Privy 会话**），闸门 `signingOut` **没升起** | 同处 |
| 5 | 于是 effect 把 profile **原样写回** → 用户点「解除」，行回来，刷新还在 | 同处 |

**修 F1 的那道闸门救不了它**：`signingOut` 只在 `handleSignOut` 里升起，而「解除 Google」按语义
**不该结束整个会话**（那会把钱包与其余两轨一起登出）。所以这不是"忘了套用 F1 的修法"，
而是**同类缺陷的第二条路径**——需要自己的终止条件。

### 2.2 修法：把"用户的移除"做成**在能活过一次重跑的事实**，闸门下沉到写入通道

新增在 `src/lib/authState.ts`（纯函数层，不起在组件里——因为要挡的那个写入方**不是**这个组件）：

```ts
export function unlinkRail(rail): void;          // 用户路径：清行 + 记下这个身份
export function heldUnlinkedIdentity(): string | null;  // 自动写入方要跳过的身份
export function releaseUnlinkedIdentity(): void;         // 显式登录/登出时解除
```

`writeAccountState` 在**幂等守卫之前**多一道：

```ts
const held = heldUnlinkedIdentity();
if (held !== null && next !== null && writeKey(value) === held) return;
```

**为什么闸门必须在这个高度**：必须被挡住的写入方是（a）bridge effect，而（b）任何"重新挂载、
第二个标签页、将来某个新组件"也会做同一件事。把闸门写在 bridge effect 里只能挡住（a），
而 F5 刚教过一次这个教训——**判据/闸门与它声称守的东西必须是同一个**。
`writeAccountState` 是**每个写入方都已经经过的唯一通道**（`050` 的幂等守卫也是这么下沉的），
所以闸门放在那里，`held` 对**调用方是谁**无感知。

**键怎么取**：`unlinkRail(rail)` 从**库里那一行**读回身份（Google 走 `googleRowKey`，
GitHub/Steam 走裸串），**不由调用方传**。理由：让调用方拼键，就等于让调用方复刻一遍拼法，
拼错时抬起的是一个**谁都写不出来的键**——一个永远不咬的闸门，正是"失败即静默"。

### 2.3 终止条件，以及**为什么它不会再假**

「粘住」的代价是可能**粘死**：用户解除后再登录，写入被闸门拒掉，于是再也登不进去。
两条终止条件，各自对应一个**真实的用户动作**：

| 终止条件 | 谁触发 | 为什么它一定会发生 |
| --- | --- | --- |
| **显式登录/登出** | `handleGoogleLogin` / `handleGithubLogin` / `handleSteamLogin` / `handleSignOut` 各自先调 `releaseUnlinkedIdentity()` | 这是**用户自己**要求改变会话状态的动作，也是唯一能改变 `privyUser` 内容的动作。**解除之后想重新登录**走的就是这条路 |
| **TTL（10 分钟）** | `heldUnlinkedIdentity()` 每次调用读 `Date.now()` | 兜底：标签页停在那儿不动的情况 |

**为什么 TTL 允许存在**（这是最容易被问"那不就白修了"的一跳，必须写清）：
它只在**同一个标签页里 10 分钟没有任何用户动作**时到期。而"写入被闸门挡住"这件事只发生在
**同一次挂载内、闸门还立着的时候**——bridge 的写入是 React 上下文更新驱动的，量级是**毫秒**，
不是分钟。若用户先登出，`handleSignOut` **在自己那一次执行里**就已经把闸门撤了；
若用户再登录，登录入口同样在**点击的当次执行里**撤闸门。
所以 TTL 到期时，能发生的只剩"用户什么都没做"，**而那时没有任何写入方在往回写**。

**为什么我不用 Privy 官方的 `unlinkGoogle` 直接掐掉来源**：`@privy-io/react-auth@3.48.1` 的
`index.d.ts:929` 确实有 `unlinkGoogle(subject)`，但注释写明 **`@deprecated Use the useUnlinkOAuth
hook instead`**，而本仓没有挂那个 hook（`Providers.tsx` 的 `usePrivy()` 只取
`login/logout/linkGoogle/linkGithub/linkWallet`）。
**本轮不引入新 API、不改 `Providers.tsx` 的契约**：`unlinkGoogle` 的语义是"从 Privy 用户上摘掉这个
社交账号"，与"把本地这一轨解绑"并不等价（前者还会在只剩一个账号时失败），换上去是**又一个未验证的赌注**。
留作**未竟项**登记（§6）。

### 2.4 判据：行为级（不需要渲染器）＋ 一处源级

`050` 把这类缺陷卡在"无渲染器"上。F7 **不必**卡在那里：bridge 对存储做的写入**只有一条**，
把它按同样的值重放一遍，就是那条缺陷路径可以被执行的部分。

| 用例 | 断言的事实 | 测不到 |
| --- | --- | --- |
| `refuses every write that would re-create the unlinked identity` | 解除后，**bridge 形态的写入**（`googleId` 拼法）、**exchange 路由形态**的写入、以及只带 `googleId` 的第三种写入，**都写不进去**；库里仍是 `null` | React 是否**真的**重跑了 bridge effect |
| `holds the key the writers spell, not the one the navbar derives` | 行里的 `id` 与 `googleId` 不一致时（`EditProfileModal` 会产生这种行），闸门抬的是 `googleId` 那一个；GitHub 轨以裸串抬/咬 | — |
| `lets the user sign back in, and lets Sign Out stand down` | 两条终止条件都真的解除闸门 | — |
| `holds now, and is gone once its TTL has passed` | TTL 前咬住，TTL 后放开 | — |
| `does nothing to a rail that holds nothing, and holds nothing either` | 空轨上不留残闸门（否则会拒掉下一次真实登录的第一次写入） | — |
| `routes the provider's unlink through the holding removal`（源级） | `KolianceAuthProvider` 的 `unlink` 调 `unlinkRail(rail)`，且不再是裸清 | 点击是否真的走到它 |
| `does not let the navbar clear a rail behind the provider`（源级） | 组件里不存在绕开闸门的裸清三轨 | — |

> **一处诚实记录**：最后两条是**把 F5 的教训套到 F7 上**。C 的判决是"**只有这条新用例变红**，
> 其余 6 条照过"，由此推得"**没有它就会全绿**"——形状与实测过的 A0 相同（A0 是真跑）。
> 也就是说，**F5 与 F7 是同一个缺口的两个面**：一条产品路径的修复，判据只绑到了它下面的函数。
>
> **测得到与测不到的分界（照实写）**：行为用例重放的是 bridge 的**写入**，不是 React 对 effect 的
> **调度**。它证明的是更强的那个命题——"**无论 React 以什么顺序重跑，这个写入都被拒**"，
> 因为拒绝发生在 `writeAccountState` 里，与调用方和时机无关。它**不能**证明 effect 一定会重跑；
> 那一跳仍属 GAP-73（`050` §5.2 的同一句话）。

### 2.5 本轮**有意不做**的一处（并把它改回去）

修补过程中我一度把 bridge 写入的行也改了：换成 `id: did:koliance:google:<subject>` +
`creditAllowanceUSD: stored?.creditAllowanceUSD ?? 600` + `trustTier: null`，
理由是"写入应当与守卫用同一种拼法"。
**随后把三处里只有一处是必要的**，其余两处改回原样：

- `id`：**不必要**。`googleRowKey` **先读 `googleId`**（`050` §2.3 有一条用例专门钉这个顺序），
  而写入本就带 `googleId: subject`，所以守卫的键与写出的行在改前就已经一致。加一个 `id` 是
  **同一事实的第二个来源**（D4），还可能被 `googleRowKey` 之外的读法读走。**不加**；
- `creditAllowanceUSD` / `trustTier`：改回原来的 `"GOOGLE VERIFIED (PRIVY)"` 与"不写即默认"。
  把 `trustTier` 写成 `null` 会落到 `googleAccountFromProfile` 的 `"GOOGLE VERIFIED CITIZEN"` 默认值上，
  **把一个占位串换成另一个默认串**，且会让 bridge 与 exchange 路由写出的行更不一致——既不在 F5/F7 范围内，
  也没有任何判据要求它。**不动**。
- 唯一保留的结构改动是 `const subject = privyUser.google?.subject ?? privyUser.github?.subject`
  （守卫不再靠 `stored ? … : null` 判断"该不该拦"）。原写法里 `stored` 为 `null` 时整个条件为假，
  **恰好就是 effect 存在的那个场景**——"账号在"与"库里已经有它"被写成了同一个测试。这是 F5 的焦点守卫。

> **为什么不顺手一起改**：F5/F7 是**判据缺口**，不是"这一带代码都该重写"。一次把三处都动，
> 变红的用例就分不清是哪一处引起的，**下一轮的证伪者会把两件事算成一件**。这是 `050` §2.3 那次
> 教训的直接应用：**判据要对着一个真实形态，而不是对着"我写下的实现"**。

## 5. F7 的人工复核步骤（自动化判据到不了，故给出可执行步骤）

Privy 需真实 `NEXT_PUBLIC_PRIVY_APP_ID`，本机没有，故以下为**待人工执行**：

1. 配好 `NEXT_PUBLIC_PRIVY_APP_ID`，`npm run dev`，用 Google 登录 Privy → 导航栏显示用户名。
2. 打开下拉 → Google 行点「解除」。
   - 期望：行**立即**变为未绑定（"Sign In"）且**保持**；`localStorage.getItem("koliance_google_profile")` 为 `null`。
   - **改前会失败**：行在下一帧被 bridge 写回，刷新后 Google 行仍显示邮箱。
3. **不刷新**，直接硬刷新一次 → 期望仍为未绑定。
   （闸门是模块态，刷新后不再存在；此时能不能回来取决于 Privy 会话——**这正是 §2.3 说的边界**：
   本轮的修法让本地行在会话期内粘住，不改变 Privy 侧仍持有该账号的事实。）
4. 同页面点「Sign In」重新走 Google → 期望能重新绑定（**终止条件 ①**：闸门在登录入口被解除）。
5. 登录后点 Sign Out → 期望登出彻底；再次登录（**终止条件 ①** 的另一半）→ 期望正常。
