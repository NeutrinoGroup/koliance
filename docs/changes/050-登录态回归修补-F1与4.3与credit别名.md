## 1. F1 · Sign Out 被 bridge effect 当场撤销（最严重，Privy 模式下必现）

### 1.1 机制（读源码得出，非按组件名推断）

改前的 `NavAuthBadges.handleSignOut` 只有三行：

```ts
const handleSignOut = async () => {
  setDropdownOpen(false);
  signOut();                       // 同步：写三条 null，各发一次事件
  if (isPrivyEnabled) {
    await privyLogout();           // 异步：此刻尚未返回
  }
};
```

`signOut()` 把 `koliance_google_profile` 删掉，`KolianceAuthProvider` 收到事件后 `setState`，
于是 `state.google` 由非空变为 `null`。而 bridge effect 的依赖是 `[privyUser, state.google]`
——**依赖变了，effect 重跑**——此时 `await privyLogout()` **还没回来**，`privyUser` 仍非空：

| # | 事实 | 处 |
| --- | --- | --- |
| 1 | bridge effect 依赖含 `state.google` | 改前 `NavAuthBadges.tsx:178` |
| 2 | 清轨后 `state.google === null` → effect 重跑 | `KolianceAuthProvider.tsx:87-91` → `:66` |
| 3 | 改前的守卫是 `stored && stored.id === …`，`stored` 为 `null` 时**整个条件为假** → **不 return** | 改前 `:166` |
| 4 | `privyUser.google` 仍非空 → `writeAccountState("google", profile)` **把 profile 原样写回** | 改前 `:177` |

**后果**：点 Sign Out → 刷新 → **仍显示已登录**。而"半登录态"正是 049 明文要消灭的对象
（`049` §3.2 与 §6 第 4 条都写了"登出 Privy 但本地行还在"是它要避免的形态）——
即**修完 #34 又把它从另一条路放了回来**。

### 1.2 修法（三条一起，缺一不可）

```ts
const [signingOut, setSigningOut] = useState(false);

const handleSignOut = async () => {
  setDropdownOpen(false);
  setSigningOut(true);                 // ① 先关门
  try {
    if (isPrivyEnabled) {
      await privyLogout();             // ② 会话真的断掉
    }
    signOut();                         // ③ 最后才清本地
  } finally {
    setSigningOut(false);              // ④ 失败也要开门
  }
};
```

- **①闸门进依赖**：`useEffect(..., [privyUser, state.google, signingOut])` 且体内首行 `if (signingOut) return;`。
  **闸门只有进了依赖数组才算数**——否则 React 不会因它变化而重跑 effect，闸门就是个装饰。
- **②先 await 再清**：清轨是被 bridge 监听的**唯一触发源**；把它挪到会话断掉之后，触发源与观察者不再交叠。
- **④ `finally`**：`privyLogout()` 抛错时若不落闸，导航栏将**永久**无法反映下一次登录。

> **为什么选"闸门 + 重排"而不是"登出时不回写"**：单看这条路径，"登出中不回写"已经够用；
> 但闸门是**显式状态**，它同时挡住另一类路径——登出飞行途中若有新的 `state.google` 写入
> （另一标签页、或某个晚到的 effect），闸门同样能拦住。**代价是一行 `useState`**，
> 换来的是"登出意图"成为一个**可被读取的事实**，而不是散在几处判断里的隐含约定。

### 1.3 判据：**时序本身未被执行验证**（如实陈述）

本仓 `vitest.config.mts` 设 `environment: "node"`，且 **无 jsdom / happy-dom / @testing-library**
（`049` §7 与 GAP-73 已实测登记）。`handleSignOut` 是**组件内闭包**，无渲染器则**跑不了**。

本轮给的两条判据都是**结构性**（读 `NavAuthBadges.tsx` 的源码行）：

| 用例 | 断言的事实 | **测不到**的 |
| --- | --- | --- |
| `raises the gate before the rows are cleared, and releases it on failure too` | `setSigningOut(true)` 在 `await privyLogout()` 之前、`signOut()` 在 `await privyLogout()` 之后、`finally { setSigningOut(false) }` 存在 | privyLogout 是否**真的先 resolve**；React 是否**真的按序重跑** effect |
| `closes the bridge effect while signing out` | effect 体内有 `if (signingOut) return;`，依赖数组为 `[privyUser, state.google, signingOut]` | 闸门**运行时是否真的拦住**了回写 |

**这条不能被"测试全绿"读成"F1 已验"**。它测的是"修法的形状在文件里"，不是"修法在运行时成立"。
**人工复核步骤**（无 Privy 也可做前半）：见 §6.2。

## 2. §4.3 · bridge 的写-依赖环：终止条件此前只靠一条字符串相等

### 2.1 机制

改前的守卫是：

```ts
const stored = state.google;
if (stored && stored.id === `did:koliance:google:${privyUser.google?.subject}`) return;
```

比较的左边 `stored.id` 来自 `googleAccountFromProfile`，而那个函数**优先取已存的 `g.id`**：

```ts
const id = asString(g.id) ?? (googleId !== null ? `did:koliance:google:${googleId}` : …);
```

而 `EditProfileModal.tsx:107-110` 写入的是 `{ ...updatedProfile, googleId }`——`updatedProfile`
是从 `UserProfileData` 展开的，**带一个 `id`**。于是库里那一行的 `id` 与另拼的
`did:koliance:google:<subject>` 可以不一致（`name` 也会被 Modal 改写成不同值）。

**不一致时 `:166` 恒假 → 不 return → 每次写入都触发下一次重跑 → 无界循环**，
而父组件 `AgentCardTerminal.tsx:559-561` 每轮 `setCreditLimit(prev => prev + allowance)`
——**授信额度持续自增**。

> **它为什么此前没炸**：`editModalOpen` 未开时 `EditProfileModal` 的保存路径不会走，
> 且要 Privy 已登录（`privyUser.google` 非空）才会进这个 effect。**条件性**，但一踩就是无界。

### 2.2 修法：两层，互为纵深

**第一层（结构面）· 比较存进去的那一行，而不是推导后的对象**

```ts
// src/lib/authState.ts（新增）
export function storedGoogleRow(): Record<string, unknown> | null { … }
export function googleRowKey(row): string | null {
  const googleId = asString(row.googleId);
  if (googleId !== null) return `did:koliance:google:${googleId}`;
  const id = asString(row.id);
  if (id !== null) return id;
  const email = asString(row.email);
  return email !== null ? `did:koliance:google:${email}` : null;
}
```

**为什么这比原来那条相等强**：原判据比较的是**两个不同拼法的推导结果**——左边可能带 `id`、
右边恒是 `<subject>` 拼的。**这种不等是"比较本身造出来的"，不是"库里的值真的变了"**，
所以它**结构上不可能**成为可靠的终止条件。`googleRowKey` 只认**库里那一行**，
与写入方用 `googleId` 还是 `id` 无关。

**第二层（机制面）· 写入幂等**

`writeAccountState` 现在先算出"这次调用会让库里变成什么字节"，与库中现值相同则**既不写、也不发事件**。
终止条件因此**下沉到写入通道**，不再依赖调用方的守卫是否写对：

| 它避开的失败模式 | 说明 |
| --- | --- |
| 守卫被后人改错/删掉 | 事件仍然不会发，环仍然断（**这正是本轮 F1 的反面**：F1 是守卫写错了没人发现） |
| `JSON.stringify` 的字段序 | 两侧都是同一函数对同一个值的输出，序一致；**不是**"两个手写对象字面量逐字段比" |
| 缺字段 vs `undefined` | 同上：`undefined` 不产生字节，不制造假不等 |
| 依赖库里旧行的拼法 | 幂等比较的是"新字节 vs 库里字节"，**不要求旧行是本组件写的** |

### 2.3 判据

| 层 | 用例 | 变异后变红 |
| --- | --- | --- |
| 幂等 | `stays silent when the stored bytes are unchanged, and only then` · `stays silent when clearing a rail that holds nothing` · `sees a value re-read from the store as unchanged` | 注释掉幂等守卫 → **2 条红** |
| 键 | `gives the exchange route's row and a re-spelled row the same key` · `is null for an empty store and for a row that identifies nobody` · `keys off googleId when a row carries a disagreeing id` | 键改成 `id` 优先 → **1 条红** |

> **一次诚实记录（照实写）**：`googleRowKey` 的 key 顺序（`googleId` 优先）**第一次做变异时没被抓住**
> ——因为当时没有任何用例构造"`id` 与 `googleId` 不一致"的行。**这不是变异选得不好，是该判断当时不可证伪**。
> 补上 `keys off googleId when a row carries a disagreeing id` 之后变异才变红。
> 教训与 `049` §4.3 的自查同族：**判据要对着一个真实形态，而不是对着"我写下的实现"**。

## 3. 口径 · `creditAllowanceUSD` 缺 snake 别名

`001_init_and_composite_indexes.sql:92` 的列名是 **`credit_allowance_usd`**，
`src/lib/db.ts:22` 的 `DbUserRecord` 同拼法，而 `GET /api/user/profile`
（`src/app/api/user/profile/route.ts:73`）返回的是 `fetchUserFromDatabase` 的
`select("*")` 结果——**列名，不是 JSON 键名**。

`googleAccountFromProfile` 此前只认 `g.creditAllowanceUSD`，而**紧邻的
`wallet_address` / `trust_tier` 都有 snake 别名**。于是整行从 DB 读回时，
授信额度**静默落回默认 600**。

**它不是装饰性数字**：`NavAuthBadges.tsx:350` 渲染它，`AgentCardTerminal.tsx:560`
把它加进卡片授信上限。**一条拼法不一致让"数据库里的真实额度"在界面上变成另一个数**。

**修**：补 `credit_allowance_usd` 别名，顺序与既有两处对称（camelCase 优先）。
**连带**：`synthetic` 同因一并折叠——DB 里是 `1`，而 `select("*")` 交回的也是列值，
`g.synthetic === true` 对 `1` 为假，会把合成行**显示成已授信的真实身份**。

**判据**：5 例（含"0 不被默认值吞""两种拼法都在时以 JSON 拼法为准""两种都没有才落 600"）。
变异：删掉别名 → **3 条红**。

## 4. F2 复核：**有** —— 且总控的零命中是**命令的问题**，不是代码的问题

falsifier 称 `GoogleAuthWall.tsx:60` / `GitHubDevWall.tsx:80` / `AgentCardTerminal.tsx:184`
有硬编码的 `localStorage.getItem("koliance_...")`；总控 `git grep` 报**零命中**。

**在本仓内实测：三处字面量确实都在**，逐字与 falsifier 的描述一致：

```
$ git grep -n "koliance_google_profile" -- src          # 本仓内
src/components/GoogleAuthWall.tsx:60:      const cached = localStorage.getItem("koliance_google_profile");
src/lib/authState.ts:98:  google: "koliance_google_profile",
```
（另两处：`GitHubDevWall.tsx:80` · `AgentCardTerminal.tsx:184`，见 §5 的枚举）

**零命中的成因（实测，非推断）**：`koliance` 是**嵌套的独立 git 仓**，
框架外层根对它不跟踪——

```
$ git ls-files koliance | Measure-Object -Line      # 在框架外层根
0
$ git grep -n "koliance_google_profile" -- koliance
exit=1（无输出）
```

`git grep` 只扫**自己索引里的路径**，而 `koliance/` 在外层仓的索引里**一个文件都没有**，
所以它扫不到任何东西。**`exit=1` 被当成了"代码里没有"，实际是"命令没扫"**——
这正是 D1 点名的形态（**跑不动的命令的失败读数不得当成结论引用**）。

**处置**：三处读改走 `STORAGE_KEYS`（D4：读也应走 SSOT）。
**并且把机械守卫扩到读**——原 `DIRECT_WRITE` 只匹配 `setItem` / `removeItem`，
**读这一半完全没守**，一次改名可以无声地漏掉一处读，且失败形态是"这个访客未登录"而不是一个错误。
**扩守卫前先确认它在旧形态下为红**：把 `GoogleAuthWall` 的读改回字面量，
新守卫报 `offenders = ['components/GoogleAuthWall.tsx']`（该变异记录于 §6）。

**有意不改**：`GitHubDevWall` 的 `koliance_github_client_id` / `_client_secret`、
`DeveloperConsole` 的 `koliance_developer_wallet`、`i18n` 的 `koliance_lang`、
`audit.ts` 的键——**都不是身份行**（不参与三轨身份、不经 `writeAccountState`、
不触发登录态），**不在 `STORAGE_KEYS` 的语义范围内**，随手并进来会让那个常量
从"身份行 SSOT"膨胀成"所有 localStorage 键的清单"，**反而削弱它的含义**。
