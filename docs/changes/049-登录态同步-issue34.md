## 1. 根因（**读源码得出**，非按组件名推断）

issue 给的推测是「登录态与导航栏组件状态未同步——OAuth 回调完成后导航条未刷新」。**方向对，机制不对**。
逐行读改前的 `NavAuthBadges.tsx` 后，实际是**三件事叠在一起**：

### 1.1 「导航条未刷新」的机制是**它永远不会刷新**，不是「刷新得慢」

改前 `NavAuthBadges.tsx:121-172` 的账户态是 `useState` 快照，唯一刷新口是：

```ts
useEffect(() => {
  syncAuthState();
  const handleStorage = () => syncAuthState();
  window.addEventListener("storage", handleStorage);
  return () => window.removeEventListener("storage", handleStorage);
}, []);                       // ← 依赖数组为 []，全程只跑一次
```

时序上它**必然错过**登录：

| # | 事实 | 处 |
| --- | --- | --- |
| 1 | 点 Google 登录**离开当前文档**——非 Privy 时 `window.location.href = accounts.google.com/...`；Privy 时 `linkGoogle()`/`login()` 走 Privy 自己的弹窗/跳转 | 改前 `NavAuthBadges.tsx:195-216` |
| 2 | 回来时是**整页加载**，导航栏挂载时 `localStorage` **还是空的**（兑换尚未发生），故渲染 "Sign In" | 同上 + `:539` |
| 3 | 之后 `GoogleAuthWall.handleExchangeCode` 才写入 `koliance_google_profile` | `GoogleAuthWall.tsx:80` |
| 4 | 此时挂载 effect 早已跑完；**且写方监听不到自己写的值** | 见 1.2 |

### 1.2 `storage` 事件**按规范只在其它文档触发**，同文档永不触发

这是关键的一条，也是「看起来有监听、实则没有判据」的地方：
`window.addEventListener("storage", ...)` 于**写入的那个文档**里**永远不会被调用**——
规范把该事件投递给**同源的其他文档**（多标签页场景）。
所以登录所在的那个标签页**从来收不到自己的写入**，`syncAuthState` 一次也没被登录触发过。
**这解释了为什么"加了监听"没救回来**：判据在，但它对本场景恒不触发（D3 的"失败了不会响"）。

### 1.3 三个症状各自还有独立的成因

| 症状（issue 原文） | 机制 |
| --- | --- |
| **不显示头像** | 改前的读取路径**整块丢掉了 `picture`**——`:126-136` 组对象时没写 `picture` 字段（`:95` 的注释自己写着 "Auth states stored in localStorage"）。**即使** profile 到了，头像也只能是 `User` 占位图标（`:284-286`） |
| **按钮仍是 Sign In** | `:523-549` 的 "Sign In" 按钮**只由 `googleUser` 门控**。纯钱包用户已登录时 `googleUser` 仍为 `null`，按钮照旧显示 "Sign In" |
| **登录后仍无会话**（同一根因的另一半） | `:196-201` 无条件下 `linkGoogle()` 优先。**`linkGoogle` 是给"已登录的 Privy 用户"挂 Google 账号的，它不创建会话**（SDK 类型注释：`immediately redirects to Google login page and prompts the user to link their account`）。未登录访客走完 Google 回到页面，`linkGoogle` 的结果被 Privy 丢弃，**会话根本不存在** |

### 1.4 `Privy User` 的形状是读出来的，不是猜的

`node_modules/@privy-io/react-auth/dist/dts/types-DbK0_UgU.d.ts`：

```
interface Google { subject: string; email: string; name: string | null; }   // :1204-1211
interface Github { subject: string; username: string | null; name: string | null; email: string | null; }  // :1238-1247
```

**没有 `picture` 字段**，也**没有 `id` 之外的 `googleId`**。故改前的两处都是死的：
`privyUser.google.name as string` 与 `privyUser.id`（那是 Privy DID，不是 `sub`）。
新代码改用 `subject` 作为 Google `sub`，使 **Privy 登录与直连 OAuth 落到同一个 `googleId`**，
而不是同一个人的两个账户。

## 2. 裁定：改「状态归属」，不是补一次刷新

| 选项 | 说明 | 判定 |
| --- | --- | --- |
| (a) 在 `GoogleAuthWall` 里 `window.dispatchEvent(new Event("storage"))` 通知导航栏 | 改前 `EditProfileModal.tsx:108` **已经这么写了**，而它同样对同文档无效 | ❌ 不成立 |
| (b) 让 `GoogleAuthWall` 去 refetch / 直接操作导航栏 | 子组件反向驱动父的兄弟组件；耦合方向错，且每加一个消费者就要改一次 | ❌ |
| (c) **账户态上提为共享状态，推导而非快照** | 写入方与读取方共用**一个通道 + 一个通知**，导航栏每次渲染都推导 | ✅ **采纳** |

**判据一句话**：**登录态不是"组件在挂载时读到的东西"，而是"从事实源推导出来的东西"。**
快照式（改前）在"写入发生在挂载之后"的时序下**结构上不可能正确**；推导式与此无关。

### 4.2 判据在测什么（`tests/auth-state.test.ts`，24 例）

| 组 | 钉住的事实 |
| --- | --- |
| **issue #34 主症状** | 挂载时读不到 → 写入后**下一次读就能读到**（改前这里恒为 `null`） |
| | 写入**通知同文档订阅者**（改前 `storage` 对同文档恒不触发）；退订后不再触发 |

| | Privy 身份优先于陈旧的本地行 |
