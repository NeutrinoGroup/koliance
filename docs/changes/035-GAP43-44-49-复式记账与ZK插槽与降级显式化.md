## 3. 计划做法（动手前立，落地后与实现核对）

### 3.1 A3：`005_settlement_ledger.sql` + `internal/settlement`

RFC §4.2.2 的表结构可直接用，但**原文没有「平不平」的判据**——只建表等于把一个财务公式放进仓库而不验证（D3）。
故 A3 拆成两半：

| 半边 | 落点 | 作用 |
| --- | --- | --- |
| 结构 | `backend/migrations/005_settlement_ledger.sql` | 表 + 约束（单边、非负、账户枚举）+ `balance_after` 由触发器推导 + RLS（对齐 002 的既有口径） |
| 规则 | `backend/internal/settlement/ledger.go` | **同一套规则的可执行版本**：`Journal.Append` 逐笔校验 |

**不变量（一句话）**：同一 `intent_id` 下的分录按 `ledger_id` 顺序回放时，
**任意前缀**的「贷方合计 − 借方合计」都必须为零。
（等价于「借贷必须平」；按前缀而非按总额，是为了让**每一笔**不平衡都当场暴露，而不是被后续分录冲平掩盖。）

**两处刻意设计**：

1. **`balance_after` 取其本义**——RFC 原文只给 `balance_after NUMERIC(36,18) NOT NULL`，
   **未说清是哪一层余额**（用户总余额？账户余额？）。本项目取**该 `(intent_id, account_type)` 的累计余额**：
   它可由该 intent 的历史完全复算，因此**可被机械断言**；用户总余额跨 intent，无法由单表复算。
   该偏离在迁移文件的注释里写明（D4：一处事实、一处声明）。
2. **money 用 `math/big.Rat`，不用 `float64`**，也**不引入新依赖**（`shopspring/decimal` 属重依赖决策，`ADR-004` D2 同源）。
   `big.Rat` 对十进制字面量是精确的，加法与比较无漂移。

### 3.2 A4：`internal/verifier` + 一处调用点

- `Verifier` 接口：`Scheme() string` + `Verify(ctx, Request) error`。
- `NoopVerifier`：**返回 `ErrNotImplemented`**，绝不返回「通过」。
- 调用点：`httpapi` 新增 `POST /api/v1/verifier/verify`（**纯新增路由**，不动既有路由语义），
  `Deps` 增加 `Verifier` 字段；`main.go` 注入 `NoopVerifier`。
- 默认部署下该路由对**任何**输入返回 **501**（诚实：没有接校验器），
  注入替身后「有效证明 → 200 / 无效证明 → 400」——**这才证明它不是写死的**（负向判据见第 4 节）。

### 3.3 T3：`database.New` 改为 `New(ctx, dsn) (*DB, error)`

- 无凭据 → `ErrDatabaseRequired`（显式错误，**不回显 DSN**）。
- 连接/探活失败 → 同样返回错误，**不再回落内存态**。
- `MemoryStore` 保留，但**只能显式构造**（`NewMemoryOnly()`，供测试与离线工具）。
- `main.go`：拿到错误即 `log.Fatalf`（非零退出）。
- 「业务路由不得返回 200」的负向判据按**两层**给（见第 4 节）。

### 5.6 与动手前计划的**偏离**（必须写明）

| 计划（§3.1 / §4） | 实际落地 | 为什么改 |
| --- | --- | --- |
| 不变量写成「**任意前缀**净额为零」 | 改为**每个 intent 的试算平衡**（借方合计 == 贷方合计） | 计划里的 ±0 表述**是错的**：一笔普通转账天然留下 `AVAILABLE_BALANCE=+100` / `SETTLEMENT_CLEARING=-100`，**任一笔本身就不平**。按原表述实现会**拒绝正确分录**。试算平衡是会计上"借贷必平"的本来含义，且**可机械断言**。计划中的 N1 预期"每条分录平"同错，已随之更正为「平的那条按构造即平」 |
| N1「删掉贷方 → 报错」 | **用例保留且变大** | 删掉贷方后，剩余那条是**合法分录**，错在 **intent 层**——这正是试算平衡的职责。故 N1 断言的不是"分录非法"，而是"**借方≠贷方**"，用例名 `TestUnbalancedOneSidedIntentIsRejected` 已如实反映 |
| `Journal.Append` 逐笔即校验平衡（初稿） | `Append` 只校验**单笔结构**，`Close` 才断言试算平衡 | 见 ledger.go 的 `Journal` 注释：三腿凭证（100 = 98 + 2）在写完第 2 腿时**必然不平**，逐笔断言会**拒绝正确凭证** |
| 计划未预见 | **触发器名字序** 缺陷（两个同时机触发器按字母序触发） | 静态审查抓到并**在落地前修掉**（改成单函数单触发器）。**这是 GAP-51 的实证**：该缺陷任何 Go 单测都发现不了，只有真跑 PG 才会暴露 |
