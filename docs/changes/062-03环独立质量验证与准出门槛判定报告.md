## 3. 核心判据与边界断言实测审计

### 3.1 12 错误码全可达性（ADR-006 §3.6.2 / §4.1 P3 / §4.2 N4）
在 `backend/internal/httpapi/errors_test.go` 中，`TestEveryErrorCodeIsReachable` 验证了闭集词表中的每一个项：
1. `INVALID_REQUEST` (400) -> 真实路由 `GET /api/v1/liquidations?limit=-1`
2. `INVALID_PROOF` (400) -> 真实路由 `POST /api/v1/verifier/verify` 注入 `ErrInvalidProof`
3. `UNAUTHORIZED` (401) -> 真实路由 `GET /api/v1/agentcard/cards/card-test` 无 token
4. `QUOTA_EXHAUSTED` (403) -> 构造调用 `writeError` on quota refusal
5. `RESOURCE_NOT_FOUND` (404) -> 构造调用 `writeError` on missing resource
6. `METHOD_NOT_ALLOWED` (405) -> 真实路由 `DELETE /api/v1/liquidations` (methodOnly)
7. `RATE_LIMITED` (429) -> 构造调用 `writeError` on rate limit exceeded
8. `INTERNAL_ERROR` (500) -> 构造调用 `writeError` on internal failure
9. `VERIFIER_UNAVAILABLE` (503) -> 真实路由 `POST /api/v1/verifier/verify` 注入 nil verifier
10. `UPSTREAM_UNAVAILABLE` (502) -> 构造调用 `writeError` on upstream timeout
11. `DATABASE_UNAVAILABLE` (503) -> 真实路由 `POST /api/v1/game/proof` 注入 nil DB
12. `SERVICE_NOT_CONFIGURED` (503) -> 真实路由 `GET /api/v1/market/prices` 缺 Alpaca 凭据

**断言严格性核实**：
- 严格断言 HTTP 状态码一致；
- 严格断言响应头 `Content-Type: application/json`；
- 响应体 JSON 严格包含 `code`、`error` 与非空 `requestId`；
- 业务文案严格与 `errorCopy` 闭集英文字符串逐字比对；
- 验证 `writeError/<CODE>` 针对全量 12 码的标准 3-key（`["code", "error", "requestId"]`）闭集信封；
- 验证原始错误详情（`rawErr`）成功记录在日志的 `err` 字段中。

### 3.2 P4 字节级不变性（ADR-006 §4.1 P4）
在 `backend/internal/httpapi/reqlog_test.go` 中，`TestLoggingMiddlewareDoesNotAlterBody` 跨越 8 类请求模式进行裸 handler 与中间件包裹 handler 的对拍断言：
- `GET 200 via jsonResponse`
- `GET 503 refusal via jsonError`
- `GET 204 with no body`
- `GET body written in two calls, implicit 200`
- `POST with a request body, 200`
- `POST with a request body, 400 refusal`
- `POST 204 with no body`
- `DELETE 405 from methodOnly`

**断言严格性核实**：
- `responseDiff` 逐字节比对 `bare.Body.Bytes()` 与 `wrapped.Body.Bytes()`；
- 比对状态码 `bare.Code == wrapped.Code`；
- 严格断言中间件除了追加 `X-Request-Id` 头之外，不篡改、增加或删除任何其他响应头；
- 断言日志输出中存在且仅有一条 JSON 结构化日志，记录了正确路径与响应状态。

### 3.3 N5 变异注入证伪用例（ADR-006 §4.2 N5）
在 `backend/internal/httpapi/reqlog_test.go` 中通过 `mutatedLoggingMiddleware` 实施故障注入：
- **`TestN5InjectedBodyWriteTurnsP4Red`**：
  - **Phase 1（控制基准）**：注入开关关闭，断言变异副本与真实中间件输出完全一致（保证未漂移）；
  - **Phase 2（故障证伪）**：开启注入开关，中间件在响应体头部强行写入 1 字节 `!`。断言 P4 的 `responseDiff` 必定检测出差异并报错（变红）。若未报错则用例直接 `t.Fatal`。
- **`TestN5PostOnlyInjectedBodyWriteTurnsP4Red`**：
  - 针对系统中全部 15 个 POST 写操作路由，定向注入仅在 POST 方法时写入 1 字节；
  - 证实 GET 比对保持干净（无误报），而 POST 比对精准变红（无漏报），彻底封闭了 GET-only 时代的隐蔽盲区。

### 3.4 前端信封保真与类型安全（Track 1 Step 2.3）
在 `tests/api-error-envelope.test.ts` 中针对前端适配层执行端到端契约验证：
- `parseApiError`：验证标准 3-key 信封解析、developer `errorCode` 兼容解析、`X-Request-Id` 头回退机制以及 HTML 报错（502）非 JSON 安全降级；
- `executeMarketTrade`：验证 200 OK、400 校验拒绝（`INVALID_REQUEST`）、503 凭据未配（`SERVICE_NOT_CONFIGURED`）、200 伪成功（券商下游挂掉时映射 `UPSTREAM_UNAVAILABLE`）及网络断开的错误信封保真；
- `closeMarketPosition` / `createStripeCheckout` / `authorizeMicropayment`：验证非 2xx 响应中 `code`、`error`、`requestId` 字段透传与强类型完整性；
- `/api/market` BFF 路由：验证网关拒绝时 503/404 状态透传与 `code`、`requestId` 的保真转接；
- UI 呈现：`MarketTerminal.tsx` 与 `AgentCardTerminal.tsx` 将 `code` 与 `requestId` 呈现于 Toast 与告警卡片，消除故障排查黑盒。

## 5. 质量阻断项（Gatekeeper Rule）与 03 环准出判定

### 质量阻断项（硬性门槛）
- **Gate-1（编译与竞争门禁）**：`go test -race ./...` 与 `npx tsc --noEmit` 必须 0 错误、0 race。
- **Gate-2（覆盖率底线门禁）**：`httpapi` 语句覆盖率必须 $\ge 76.00\%$，全包 Gated 总覆盖率必须 $\ge 69.00\%$。

- **Gate-4（日志与响应不变门禁）**：P4 与 N5 成对必须通过，中间件绝不得修改响应体字节。
